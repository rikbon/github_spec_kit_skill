# SDD Best Practices Guide

The quality of code generated by AI agents is directly proportional to the quality of the requirements they receive. This guide outlines standard practices for writing high-quality specifications, technical plans, and checklists under the Spec-Driven Development (SDD) methodology.

---

## 1. Writing High-Quality Specifications

Specifications should focus entirely on **what** to build and **why**, leaving the **how** (technical details) to the planning phase.

### Best Practices:
- **Avoid Tech Stack Leaks**: Do not mention programming languages, libraries, database types, or API protocol names (e.g., write "allow users to securely log in" instead of "use JWT tokens with bcrypt").
- **Write Verifiable Acceptance Criteria**: Every user story must end with clear, measurable scenarios.
  - Bad: "The system should load pages quickly."
  - Good: "The landing page must load in under 1.5 seconds under standard network latency."
- **Clearly Define Boundaries**: Explicitly state what is **Out of Scope** to prevent feature creep.

---

## 2. Writing Technical Plans

Plans should establish the technical blueprint and bridge the gap between functional requirements and execution.

### Best Practices:
- **Enforce the Constitution**: The plan must show trace-links to the principles in `constitution.md`.
- **Define Interface Contracts Early**: Specify exact request/response shapes, database schemas, and interface models under a `contracts/` folder before writing tasks.
- **Quantify Performance Constraints**: Document latency limits, scale assumptions, and dependency failure modes.

---

## 3. Designing Quality Checklists ("Unit Tests for English")

Checklists in SDD validate **requirements quality**, not implementation code.

| Aspect | Bad (Testing Code) | Good (Testing Requirements) |
| :--- | :--- | :--- |
| **UX** | "Verify that the primary button is blue." | "Are visual hierarchy and color guidelines defined for interactive buttons?" |
| **API** | "Check if the API returns 404 for missing items." | "Are error formats and status codes specified for resource-not-found scenarios?" |
| **Security** | "Ensure that passwords are hashed in the database." | "Are encryption requirements defined for sensitive user credentials?" |

---

## 4. Execution Discipline

1. **Complete Clarification first**: Never proceed to `/speckit plan` while `spec.md` still contains `[NEEDS CLARIFICATION]` markers.
2. **Commit Plan before Tasks**: Always commit your design documents (`plan.md`, `data-model.md`, `contracts/`) before generating the task list. This ensures the tasks match the finalized design.
3. **Respect Task Boundaries**: When executing `/speckit implement`, keep changes focused exactly on the files listed in the active task. Do not rewrite surrounding modules unless required by the task.
